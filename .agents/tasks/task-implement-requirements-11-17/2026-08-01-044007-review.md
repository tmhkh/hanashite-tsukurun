# Requirements 11-17: Layout variations, animations, StructureVisualizer, StepGuide, QuestionRationale, CompletionFeedback

Seven new features for the child-friendly presentation app: the backend prompt now requests layout-varied Marp output with a custom theme (`hanashite-pop`), text decoration, and a `completion_feedback` field; the frontend replaces ProgressBar with a three-state StructureVisualizer, adds a timed StepGuide card after step completion, shows a toggleable QuestionRationale hint below the AI bubble, renders CSS animations on the slide viewer, and displays a CompletionFeedback card on the finish screen. The implementation threads `completion_feedback` from Lambda response through the full React state chain and enforces empty values for non-step-3 responses server-side.

Watch for: StepGuide calls React hooks after a conditional early return, violating the Rules of Hooks — the eslint-disable comments suppress the warning but production React will break on step transitions (confirmed). The Marp markdown parser in MarpSlideViewer strips `<!-- _class: ... -->` directives and Marp frontmatter attributes (`header`, `footer`, `two-column` layout) that the backend now generates, meaning the richer layout instructions are silently discarded at render time (confirmed). The old ProgressBar component and its test remain as dead code with no importers (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

StepGuide has `useEffect` and `useCallback` placed after an early `if (!message) return null` guard. React requires hooks to be called in the same order on every render — when the component transitions from step 1/2 (hooks called) to step 3 (hooks skipped), React will throw a "rendered fewer hooks" error. The eslint-disable comments mask this at lint time but not at runtime.

The custom Marp markdown parser in MarpSlideViewer treats all non-heading, non-icon-comment lines as body text. The new backend output includes `<!-- _class: lead -->`, `<!-- _class: two-column -->`, blockquote syntax (`>`), bold markers (`**`), and `header`/`footer` frontmatter — none of which are parsed or rendered. The viewer silently flattens this enriched content into plain text, so the layout variation and text decoration features have no visible effect in the app's own slide preview.

ProgressBar (`ProgressBar.tsx` and `ProgressBar.test.tsx`) is no longer imported anywhere but remains in the tree, adding dead code and a test that runs against an unused component.

## StepGuide hooks ordering violation

The component structure in `StepGuide.tsx`:

```tsx
export function StepGuide({ step, visible, onDismiss }: StepGuideProps) {
  const [opacity, setOpacity] = useState(1);
  const message = STEP_GUIDE_MESSAGES[step];

  if (!message) {       // <-- early return for step 3
    return null;
  }

  // eslint-disable-next-line react-hooks/rules-of-hooks
  useEffect(() => { ... }, [visible]);

  // eslint-disable-next-line react-hooks/rules-of-hooks
  const handleTransitionEnd = useCallback(() => { ... }, [opacity, onDismiss]);
  ...
}
```

When `step` changes from 1 or 2 to 3, the component goes from calling `useState` + `useEffect` + `useCallback` to calling only `useState` and returning early. React tracks hooks by call index; the mismatch throws an invariant violation at runtime. The test suite doesn't exercise this transition because it mounts the component fresh for each step value rather than re-rendering with a new prop.

The fix is to move all hooks above the conditional return:

```tsx
const [opacity, setOpacity] = useState(1);
const message = STEP_GUIDE_MESSAGES[step];

useEffect(() => { ... }, [visible]);
const handleTransitionEnd = useCallback(() => { ... }, [opacity, onDismiss]);

if (!message) return null;
```

## Marp markdown enrichment is silently dropped

The backend now generates markdown like:

```markdown
<!-- _class: lead -->
# すきなどうぶつ 🐕
ぼくは **いぬ** がすきです
> ふわふわで かわいいんだよ！
<!-- icon: dog -->
```

The parser loop in `MarpSlideViewer.tsx` categorizes lines as either: heading (`# `), icon comment (`<!-- icon:`), or body text (everything else). This means:

- `<!-- _class: lead -->` → appended to body as literal text
- `**いぬ**` → rendered as literal asterisks in the `<p>` tag
- `> ふわふわ...` → rendered as literal `>` character in body

The `hanashite-pop.css` theme file is written for Marp's own rendering engine and has no effect on this custom viewer. The viewer would need either a lightweight markdown renderer (at minimum: strip class directives, render bold, render blockquotes) or an integration with `@marp-team/marp-core` to make the enriched output meaningful. The mock response in `mockResponses.ts` includes all these constructs, so users will see raw markdown syntax in the slide preview.

## StepGuide timing relative to step transition

In `MainScreen.tsx`:

```tsx
setCurrentStep(response.next_step as Step);
setAiText(response.ai_response_voice);

setStepGuideStep(currentStep);  // captures closure value of currentStep (old step)
setStepGuideVisible(true);
```

This works because `currentStep` in the closure is the pre-update value (React batches state updates within the same synchronous block). The guide correctly shows the message for the step that just finished. However, if this code is refactored to use the state-updater form or if the ordering changes, the guide step would pick up the wrong value.
